New `updateItem` server action in `src/actions/items.ts` — Zod-validated, session via `auth()`, returns the `{ success, data, error }` envelope; paired with `updateItem(userId, itemId, data)` in `src/lib/db/items.ts`, which verifies ownership with `findFirst({ id, userId })` before updating (so no coupling to Prisma's `P2025`), replaces tags via `set: []` + `connectOrCreate`, and returns the refreshed `ItemDetailData` so the drawer updates without a second fetch. Extracted `src/lib/item-form.ts` (`getEditableFields`, `buildUpdatePayload`) so the type gating is unit-testable: content for snippet/prompt/command/note, language for snippet/command, url for link; fields the form does not render are carried over from the stored item so a save never clears them. Two validation subtleties: `content` uses a non-trimming schema because indentation and trailing newlines are significant in code (a review caught the original shared schema silently stripping them — pinned with a failing test first), while title/description/language/url stay trimmed; and the form is `noValidate` so the server Zod schema is the single source of truth and its errors arrive as toasts rather than native `type="url"` bubbles blocking submit. `ItemDrawerProvider` gained `editing` state (reset on open and on close), and `handleSaved` replaces the cache entry as well as the state before calling `router.refresh()` so the server-rendered card lists follow (~1.3s). Re-added `sonner` (uninstalled 2026-05-26) for save toasts, mounted via a new `src/components/theme/ThemeToaster.tsx` that follows the app's own `dark` class and `devstash:theme-change` event instead of the OS preference — chosen over the earlier server-rendered-banner approach because the drawer stays mounted, so the 2026-05-26 subscription race does not apply. Added a `Textarea` UI primitive (base-ui has none). Tests 58 → 71 across `src/actions/items.test.ts`, `src/lib/item-form.test.ts`, and `src/lib/db/items.test.ts`; the new assertions were mutation-checked, and the tag `set` + `connectOrCreate` ordering was verified against the dev database with a throwaway probe (leaving a few orphaned `Tag` rows, which `connectOrCreate` reuses). - 2026-08-04: **Item Delete** — The drawer's trash button was a disabled placeholder; it now opens a confirmation and deletes. New `DeleteItemDialog` (client) wraps the existing `src/components/ui/alert-dialog.tsx` (hand-rolled over `@base-ui/react`, same `render`-prop composition as `DeleteAccountDialog`), names the item in its description, and ignores dismiss attempts while the request is in flight so the dialog cannot vanish mid-delete. Confirm button is labelled "Delete" rather than "Delete item" — that is the trigger's label, and duplicating it announced the same accessible name twice. Dialog sits at `z-60` over the Sheet's `z-50` (documented; portal DOM order alone would be fragile). Server action `deleteItem(itemId)` in `src/actions/items.ts` mirrors `updateItem` (`auth()` gate, `{ success, error }` envelope) and rejects a blank id with a plain `!itemId?.trim()` check — a Zod schema here would coerce, transform and report nothing. `deleteItem(userId, itemId)` in `src/lib/db/items.ts` verifies ownership with `findFirst({ id, userId })` before deleting, so a missing or foreign item returns `false` instead of coupling to Prisma's `P2025`; `ItemCollection` links and implicit tag links cascade with the row while shared `Tag` rows survive (verified against the dev DB with a throwaway probe). `ItemDrawerProvider` gained `handleDeleted`, which **evicts** the cached detail (`cache.current.delete(id)`) rather than replacing it as save does — a kept entry would let `openItem` replay a ghost with no refetch — then closes the drawer and `router.refresh()`es the server-rendered lists. Also reworked the drawer's error state into `ItemDrawerErrorState { title, message }`: a 404 now reads "Item unavailable — This item no longer exists — it may have been deleted." instead of "Something went wrong", a state reachable in the window between a delete and the list re-rendering. The 404 is checked before `response.json()` (that path never reads the body, and a 404 from elsewhere may not carry JSON), and the stale-response guard now runs after both awaits. Tests 71 → 80 in `src/actions/items.test.ts` and `src/lib/db/items.test.ts`; every new guard was mutation-checked. **First Playwright E2E layer in the project** (`npm run test:e2e`, 10 specs): `playwright.config.ts` (chromium, `workers: 1`, `webServer` reusing/starting `npm run dev`), `e2e/auth.setup.ts` which caches `storageState` and reuses it rather than re-signing-in — credentials login is rate limited 5/15m, so a fresh login each run would lock the suite out — and `scripts/e2e-item-fixture.ts`, a `tsx` subprocess CLI for DB fixtures because Playwright transpiles specs to CJS while the generated Prisma client is ESM. Every spec works on a throwaway item, so seeded data stays intact. The cache-eviction spec recreates the deleted id with a new title and navigates client-side (same layout, provider stays mounted) to prove a refetch; it was initially vacuous — an earlier attempt aborted the RSC refresh, which made Next hard-navigate, and a stale dev server reused via `reuseExistingServer` served pre-mutation code during the first mutation check. Known limitations: pages still fetch with `DEMO_USER_ID` while the action scopes to `session.user.id`, so delete works only as the seeded demo user; delete is drawer-only (no per-card action); an item deleted **out of band** (another tab/device) can still show a cached ghost, since eviction only fires for deletes made through this drawer; and the testing docs (`coding-standards.md`, `ai-interaction.md`, `CLAUDE.md`) still describe Vitest-only testing with no mention of `npm run test:e2e`. Completed 2026-08-04.
